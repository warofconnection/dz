# Сборка в Cisco Packet Tracer 8.2.2

**Статус:** текущая пользовательская модель — `clinic8.pkt` в этой папке. Файл структурно проверен; результаты тестов пользователя в Cisco находятся в `validation-results.csv`. Инструкция ниже описывает воспроизведение с нуля, собирать уже полученный файл заново не требуется. Пользовательский скриншот сохранён в ../diagrams/packet-tracer.png; невыполненные проверки отмечены отдельно.

## 1. Устройства

Разместить 6 маршрутизаторов **2911**: R-C1, R-C2, R-B1, R-B2, R-EDGE и операторский R-ISP. Разместить 7 **2960-24TT**: SW-C1A, SW-C1B, SW-C2A, SW-C2B, SW-B1, SW-B2 и операторский SW-PROVIDER.

Добавить **84 PC-PT**, **8 Printer-PT**, **4 AccessPoint-PT**, **3 Server-PT** в центре и **1 Server-PT** PUBLIC-WEB у оператора. Для проверки Wi-Fi дополнительно добавить по одному TabletPC-PT на этаж (они представляют гостей, не входят в 84 рабочих ПК). В автоматическом сценарии создаются четыре гостевых TabletPC-PT с беспроводными интерфейсами. При ручном использовании Laptop-PT без Wi-Fi нужно выключить питание, установить WPC300N и включить питание.

Названия конечных устройств, отделы и назначение портов: `ports.csv`, `../docs/cable-routes.csv`. Сначала задать Display Name, затем выполнить соединения. Представить все 84 ПК, а не заменять отдел одним условным ПК. Подписать этажи, отделы, линии, порты и пользователей: например «C1-PC01 — регистратор 1».

## 2. Магистральные соединения

| Первый конец | Второй конец | Соединение |
|---|---|---|
| R-C1 Gi0/0 | SW-C1A Gi0/1 | Ethernet trunk |
| SW-C1A Gi0/2 | SW-C1B Gi0/1 | Ethernet trunk |
| R-C2 Gi0/0 | SW-C2A Gi0/1 | Ethernet trunk |
| SW-C2A Gi0/2 | SW-C2B Gi0/1 | Ethernet trunk |
| R-C1 Gi0/1 | R-C2 Gi0/1 | Межэтажное L3 |
| R-C1 Gi0/2 | R-EDGE Gi0/0 | L3 |
| R-EDGE Gi0/1 | SW-PROVIDER Gi0/1 | Trunk 901,902,903 |
| R-B1 Gi0/1 | SW-PROVIDER Fa0/1 | Access VLAN 901 |
| R-B2 Gi0/1 | SW-PROVIDER Fa0/2 | Access VLAN 902 |
| R-ISP Gi0/0 | SW-PROVIDER Gi0/2 | Access VLAN 903 |
| R-B1 Gi0/0 | SW-B1 Gi0/1 | Trunk |
| R-B2 Gi0/0 | SW-B2 Gi0/1 | Trunk |
| R-ISP Gi0/1 | PUBLIC-WEB Fa0 | Ethernet |

ПК, принтеры, AP и серверы подключить по `ports.csv` к Fa0/x. Использовать Copper Straight-Through между разными типами устройств, Copper Cross-Over между одинаковыми; либо автоматический выбор типа связи. В модели медная межэтажная связь имитирует проектную оптическую линию OM3: штатные 2911 не предоставляют нужную физическую оптическую конфигурацию. Эти различия отразить в отчёте.

В модели порты оператора к филиалам — 100 Мбит/с. Интернет физически 1 Гбит/с, проектный тариф 200 Мбит/с не эмулируется. Из Packet Tracer нельзя выводить реальную производительность закупаемых маршрутизаторов или медицинских приложений.

## 3. Конфигурации IOS

Для каждого маршрутизатора и коммутатора открыть **CLI**, отказаться от initial configuration dialog (`no`), дождаться приглашения и вставить соответствующий файл из `configs/`. Если консоль уже находится в режиме `(config)#`, сначала выполнить `end`. Проверить отсутствие `% Invalid input`, `% Incomplete command`, `% Ambiguous command`. Конфигурации являются подготовленными, а не проверенными на настоящем IOS.

После загрузки проверить `show ip interface brief`, `show ip route`, на коммутаторах `show vlan brief` и `show interfaces trunk`. В списке рабочих VLAN присутствуют 10/20/30/90/99 в соответствии с этажом. Подключённые пользовательские порты включены, остальные отключены. Подождать сходимости Ethernet/STP.

Сети: `10.s.v.0/24`, шлюз `.1`, где s=1 (C1), 2 (C2), 11 (B1), 12 (B2); v=10 (медицинская), 20 (регистратура/администрация только центр), 30 (серверы только C1), 90 (гости), 99 (управление). ПК — DHCP. Принтеры — `.20` и `.21` в VLAN10; маска 255.255.255.0, шлюз `10.s.10.1`. Управление коммутаторами `.2` и `.3` VLAN99.

Гостевой ACL разрешает DHCP, запрещает назначения 10/8, разрешает внешний трафик. DHCP назначает гостям внешний DNS 203.0.113.10. NAT работает только на R-EDGE при выходе в VLAN903. Внутренний межфилиальный трафик не транслируется.

## 4. Серверы и Wi-Fi: настройки через GUI

Все серверы: Desktop → IP Configuration → Static.

| Сервер | IP/24 | Шлюз | DNS | Службы |
|---|---|---|---|---|
| SRV-MIS | 10.1.30.10 | 10.1.30.1 | 10.1.30.11 | HTTP: страница «Учебная МИС поликлиники № 8» |
| SRV-MAIL | 10.1.30.11 | 10.1.30.1 | 10.1.30.11 | DNS; EMAIL SMTP/POP3, домен clinic8.test |
| SRV-FILE | 10.1.30.12 | 10.1.30.1 | 10.1.30.11 | HTTP: страница «Учебный архив исследований» |
| PUBLIC-WEB | 203.0.113.10 | 203.0.113.1 | 203.0.113.10 | HTTP и DNS: внешний учебный ресурс |

На SRV-MAIL → Services → DNS: On; A-записи `mis.clinic8.test` → 10.1.30.10, `mail.clinic8.test` → 10.1.30.11, `files.clinic8.test` → 10.1.30.12, `www.example.test` → 203.0.113.10. На PUBLIC-WEB включить DNS и добавить `www.example.test` → 203.0.113.10. На SRV-MAIL включить EMAIL, задать домен `clinic8.test`, создать учебных пользователей `c1`, `c2`, `b1`, `b2`; учебные пароли задать локально, реальные пароли не использовать. На выбранных ПК настроить Desktop → Email: адрес соответствующего пользователя, incoming/outgoing server `10.1.30.11`.

Точки доступа подключены исключительно к VLAN90. На AP задать разные SSID: `Clinic8-C1-Guest`, `Clinic8-C2-Guest`, `Clinic8-B1-Guest`, `Clinic8-B2-Guest`; выбрать WPA2-PSK, если оно доступно для выбранной модели. При отсутствии этой настройки выбрать совместимый AP с WPA2 или явно указать ограничение модели; не называть открытый Wi-Fi защищённым. На ноутбуках выбрать SSID и DHCP. Точку управления AP в этой модели отдельно не выделяют: это отличие от реального проекта с VLAN99.

## 5. Приёмочные проверки

Результаты записать в `validation-results.csv`: дата, исходное устройство, действие, фактический результат, статус. Ни одна проверка сейчас не отмечена пройденной.

1. На ПК каждого задействованного VLAN получить DHCP-адрес нужной /24 сети, шлюз и DNS; минимум C1 VLAN10/20, C2 VLAN10/20, B1 VLAN10, B2 VLAN10. Отдельно проверить гостевые VLAN90 всех четырёх этажей.
2. С C2-PC01, B1-PC01 и B2-PC01: `ping 10.1.30.10`, затем открыть `http://mis.clinic8.test` и проверить именно текст страницы МИС. Первый ping может не пройти из-за ARP; повторить, но записать причину.
3. Между B1 и B2 проверить ping по фактически выданным адресам ПК; адреса заранее не угадывать.
4. На C1, C2, B1 и B2 открыть `http://www.example.test`; проверить текст внешнего сервера и `show ip nat translations` на R-EDGE.
5. Отправить почту b1 → c1 и c2 → b2; на получателях выполнить Receive и проверить содержимое письма.
6. На гостевом ноутбуке каждой площадки: внешний HTTP доступен, `ping 10.1.30.10` и внутренний HTTP недоступны. Проверить счётчики `show access-lists` на соответствующем этажном маршрутизаторе; проверить DHCP повторно после продления.
7. Проверить доступ ПК к принтерам своего этажа (ping). В Packet Tracer не заявлять проверку настоящей печати.
8. Сохранить `clinic8.pkt`, закрыть, заново открыть и повторить проверки 2, 4, 5, 6. Записать версии Packet Tracer и количество конечных устройств.

Сделать настоящий скриншот Logical Workspace с подписями и поместить `../diagrams/packet-tracer.png`. Заменить им эскиз на слайде 13; убрать отметки о незавершённой модели только после проверки. Отчёт нельзя считать готовым к сдаче без `.pkt` и скриншота.
